# 根拠に基づく種目別トレーニング生成ロードマップ

作成日: 2026-09-03

## 目標

週間計画の時間枠・選択済み環境・実績を使い、ランニング、インドアバイク、自宅トレーニング（自重）について、実行可能で説明可能な具体的メニューを提案する。LLMは候補の選択と自然言語の説明に使い、能力推定、上限、安全判定、数値レンジは決定論的ロジックと検証で担保する。

出力例は、ランニングならイージー走・ペース走・インターバル・ウェーブ走、バイクなら心拍ゾーンを用いた持久走・テンポ・短い高回転、 自重ならスクワット・ランジ・体幹・プッシュアップ等を組み合わせた時間／セット／休息である。

医療的な診断、最大心拍・閾値の断定、痛みを押しての高強度提案は扱わない。痛み、体調不良、データ不足では回復・技術・短時間メニューへ保守的に寄せ、必要時は追加の計測またはユーザー確認を求める。

## Phase 0: 設定画面とデータ境界の安定化（今回）

- 時間枠、屋外可否、選択環境、週末強度希望をモバイルで編集・保存できるようにする。
- Firestoreを現在値、BigQueryを追記型履歴として維持し、JSON列はストリーミング書き込み時に明示シリアライズする。
- 入力は種目・環境を表す構造化IDだけを生成へ渡す。予定や健康に関する自由記述をログへ出さない。

完了条件: 朝ラン・夜インドアバイク・自宅トレーニングを別slotとして保存し、次回計画入力に含められる。

## Phase 1: 実績からの保守的な基準値（Performance Profile、実装済み・shadow）

### ランニング

- 直近8〜12週の有効なRunから、距離、移動時間、平均ペース、平均心拍、標高、欠損率を集計する。
- まずは平坦に近い一定走を優先し、外れ値、停止時間が多いActivity、極端な登り、古い記録を除外または低い信頼度にする。
- `easy/steady/quality`のペース・心拍レンジは単一点ではなく幅で保持する。心拍がない場合はペースと主観強度を使い、どちらも不足なら時間だけを処方する。
- 連続した高強度日、急な週間量増加、体調不良時は、推定値にかかわらず制限する。

### インドアバイク

- Strava Activityの種目、時間、平均／最大心拍、可能ならpower・cadenceを集計する。
- FTPや最大心拍をデータから断定しない。明示入力または十分な検証済みデータがない場合は、心拍の相対ゾーン、会話可能度、RPE、時間で処方する。
- 心拍ドリフト、直近負荷、休養状況を使い、テンポ・持久・回復の時間上限を決める。

### 自宅トレーニング（自重）

- 完了履歴、実施時間、RPE、部位、ユーザーの器具・環境から開始レベルを決める。
- 初回はフォームを重視する少ないセット・余力を残すRPEで開始し、完了と主観負荷が安定してから回数／セット／難易度を一段ずつ上げる。

`performance-profile-v1`を実装済み。直近84日のActivityからランニングとサイクリングのProfileを計算し、根拠Activity ID、対象期間、信頼度、除外理由、ペース／心拍／時間の幅を週間計画の不変`input_snapshot`へ保存する。Profileは現時点ではshadow入力であり、ユーザー向けの数値処方や医療的な判定には使わない。

完了条件: `PerformanceProfile`に値の根拠Activity ID、対象期間、信頼度、算出versionを保存し、集計の単体テストで外れ値・欠損・cold startを検証する。

## Phase 2: 種目別メニューカタログと決定論的処方

- `WorkoutTemplate`をversion付きで導入し、必要環境、屋外可否、所要時間、強度、禁忌、ウォームアップ／メイン／クールダウンを構造化する。
- ランニング: easy、ペース走、短いインターバル、ウェーブ走を、Profileのレンジとslotの時間から組み立てる。
- バイク: 回復、有酸素、テンポ、ケイデンスドリルを、心拍／RPE・時間で組み立てる。
- 自重: 全身、下半身、体幹、上半身の安全な基本テンプレートを、セット・回数・休息で組み立てる。
- Template選択後に、slot時間、環境、週間負荷、回復、同日2メニュー制限を検証する。数値が不確実なら強度を下げるか質問へ切り替える。

完了条件: LLMなしでも選択環境に適合する安全な候補を再現可能に生成し、無効な環境・時間超過・高強度連続をテストで拒否できる。

## Phase 3: LLMによる週間配分と説明

- LLMへは、検証済みのProfileレンジ、利用可能Template、slot、目標、直近負荷の要約だけを渡す。
- LLMはTemplateと日程の選択、週間バランス、ユーザー向け理由を返す。ペース・心拍・セットはPhase 2の許容範囲を越えられない。
- 出力後に、種目・環境、時間、同日組合せ、週間量、回復間隔、強度を再検証する。不正時は決定論的fallbackへ戻す。

完了条件: ラン＋バイク＋自重が混在する週で、朝夜の環境制約に適合し、各数値にProfileまたはTemplate由来の説明を表示できる。

## Phase 4: 実績照合と漸進的な更新

- Strava／手動ActivityとPlannedWorkoutを明示link優先で照合し、曖昧な朝夜候補はユーザーに確認する。
- 実施量、心拍、RPE、完了率を用いてProfileと次週の負荷を小さく更新する。単回の失敗や悪天候を能力低下・嗜好と断定しない。
- 提案、根拠、Profile version、Template version、照合結果を追跡し、ユーザーが手動訂正できるようにする。

実装状況（2026-09-03）: 明示的なPlannedWorkout link、同日候補の種目・時間・距離・開始時刻による照合、候補選択による手動訂正、重複候補と未実施候補の確認は実装済み。`workout-matcher-v2`では予定開始から3時間を超えるActivityを、他の指標が一致しても自動確定せず、候補として残してユーザー確認を求める。次の小項目は、確定済み照合とRPE／心拍を用いた次週負荷の小幅な更新根拠を不変の計画入力へ追加すること。

完了条件: 計画と実績の対応根拠を保存し、次週の処方変更がどのデータに基づくか説明できる。

## 実装順とガードレール

1. Phase 0を本番安定化後に確認する。
2. Phase 1は集計のみをshadowで実行し、ユーザー向け数値をまだ変えない。
3. Phase 2でカタログと安全な非LLM候補を先に完成させる。
4. Phase 3でLLMを制約付き選択器として導入する。
5. Phase 4で実績による更新を小さく開始する。

各Phaseでtimezone、データ欠損、心拍異常値、活動種別の誤分類、痛み、同時編集、再送、Strava遅延をテストする。外部Webからのメニュー取り込みは、出典・取得日・ライセンス・レビュー状態を持つ別パイプラインで管理し、計画生成時の無制限な閲覧は行わない。
